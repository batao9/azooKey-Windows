# 英単語の混在変換（実験的機能）

Issue: https://github.com/batao9/azooKey-Windows/issues/203

詳細設定の「英単語の混在変換」（`general.experimental_mixed_input`、既定OFF）を有効にすると、日本語ローマ字入力の中の対応英単語を原綴りで残す。

```text
kyouhagoogledekensaku → 今日はgoogleで検索
kyouhagithubnipushshita → 今日はgithubにpushした
```

## 初期対応と区間推定

`MixedInputConversion.swift` の独自の種語彙と、データから事前生成した英単語索引を使う。現在のローマ字テーブルで完全に日本語として読める語は自動英字化の対象から外す。`sushi`・`make`・`api` 等の曖昧な語、未知の固有名詞は既存の Shift 一時英字入力や F10 を利用できる。

### 組み込み辞書の設定

変換設定の「英単語辞書」（`general.english_dictionary`）と「カタカナ英語辞書」（`general.katakana_english_dictionary`）はそれぞれ既定ON。英単語辞書をOFFにすると、追加の英語綴り候補と種語彙を含む自動英単語認識を無効にする。カタカナ英語辞書は「アプローチ → approach」などの追加候補を制御する。元の日本語辞書、学習、ユーザー登録、F10や直接英字入力は別に保持する。

辞書変更は次のcompositionから反映する。入力中の変更では、設定操作中に次の辞書を準備し、現在のraw入力・候補ID・snapshotを維持する。確定・キャンセルのClearTextで準備済みの状態へ切り替え、キー処理中に辞書生成やファイル読込をしない。再変換と補助変換器も同じ辞書構成を使う。

一次データ・出典・利用条件は `data/english-dictionaries/`、生成した認識索引はSwiftPMの `Resources/english-vocabulary.bin` に置く。`EnglishVocabulary.swift` にデータは埋め込まない。詳しい配置・生成・検証手順は [辞書データのREADME](../data/english-dictionaries/README.md) を参照。

ローマ字互換の英字列に対して、日本語として読める区間・英単語・未解決文字のコストと日英切替コストを比較する。元の大文字小文字は変更しない。初期方式は日本語の音節としての成立性を使う保守的な区間推定であり、汎用の日英文脈モデルではない。

### 技術用語と助詞

Git・ビルド/デバッグ・言語/パッケージ管理・データベース・通信・並行処理の用語を含む独自語彙を持つ。例として `gitwotsukau` → `gitを使う`、`dockerdenodejswougokasu` → `dockerでnodejsを動かす`、`inputwooutputniwatasu` → `inputをoutputに渡す` を扱う。

実際のローマ字テーブルで語の終端を確定しても英字が残る登録語については、後続が日本語の助詞として読める境界を優先する。`git|wo` を `gi|two`（ぎとぉ）に戻さない。`token` のように終端の `n` を確定すれば日本語として読める語には、この優先を適用しない。`resetto` の促音を `reset|to` に切り直すボーナスも与えない。

語彙に名前があっても、そのテーブルで完全にかなになる語は自動判定対象とは限らない。小文字の `api`・`file`・`cache`・`rebase`・`ubuntu` 等は日本語優先の範囲に含まれる。略語、記号を含む言語名、未登録の識別子/URL/パスについては、完全自動判定と明示的な英字入力を区別する。

- 入力要素は最大256、1つの日本語区間の探索は最大16入力要素。上限を超えたcompositionは既存の入力状態を維持する。
- 英語の検索は事前構築したtrieを用い、候補語がなければ日本語区間の探索を省略する。
- ローマ字音節の判定は最大16文字のキー・最大512件のメモ化を用い、同じテーブルの再探索を抑える。テーブルや辞書構成の変更時に無効化する。
- キー入力中にディスク・外部通信・OSスペルチェッカーを呼び出さない。
- ローマ字入力等の変更時は既存のcompositionリセット契約に従う。組み込み辞書のON/OFFのみなら、上記のcomposition境界で適用する。

## canonical inputと文節編集

英字と判定した入力要素には、専用の空マッピングテーブルを示すstyleを付ける。入力文字・入力要素数を保ち、canonical `ComposingText` から候補と編集境界の両方を生成する。手動の `.direct` と、エンジンがかなの内部編集で生成するfrozen要素は自動判定と区別する。

- Shift+←/→では同じ `inputIndexToSurfaceIndexMap` を参照し、英字1文字も境界として扱う。候補の文字列だけを差し替えない。
- 英字の削除は表示中のliteral状態で行う。`google` の最後の `e` を消したとき、`le → ぇ` を経由して2入力文字を失わない。
- 英字区間内への挿入、削除で残る断片、部分確定で切り取られた英字の後半はprotected literalとして保持する。完全な辞書語でなくなっても日本語へ戻さない。
- 文節操作・候補照会だけでは日英判定をやり直さない。snapshotは元のstyleとカーソルを保持する。
- 遅延 `n` の候補消費数補正はliteralに適用しない。例えば `input` の `inp` は原入力3要素を消費する。
- `nihon|google` のような切り替えでは、実際のローマ字テーブルで終端を確認し、元入力 `n` を1要素のまま `ん` として表示する。英字先頭を日本語側へ消費しない。
- 挿入・部分確定の既存レスポンスへcanonical raw inputを付け、クライアントの予測文字列を同期する。途中への挿入をローカルの末尾追加で済ませない。部分確定後に操作ledgerを表示文字列の直接入力へ置き換えない。
- 内部編集の分離には同じローマ字テーブルの別名styleを使い、不可視のseparator入力要素を増やさずに右側の読みを保持する。混在変換ONの編集レスポンスでcanonical rawが欠けた場合は、推測で進めず復旧へ回す。

英字を含むcanonical readingは既存エンジンの英語未知語ノードでまとめて扱う。Zenzaiの有無によらず、英字部分の綴りと候補の対応範囲を検証する。

### 明示変換後の継続入力

F6〜F10・Ctrl+T等で表示を指定した後やSpace変換後に次の文字を打つときは、以前の表示全体を確定し、新しい文字だけを未確定入力として扱う。例えば `api` → F10 → `wotsukau` は `apiを使う` とする。

この切り替えでは、1キー内でTSF compositionを終了・再開始しない。IMM32アプリでは以前の結果/終了通知が新しいcompositionまで終了させ、`apiwお使う` のようにローマ字が分断されるため、新しい表示を準備してから既存の開始境界をUTF-16表示長で移動する。

確定する文字列は候補の後続表示も含めて操作に保持する。サーバー復旧が先頭候補を変えても、選択した表記を変えない。サーバー処理はclear→確定予定の文脈→新入力の順とし、成功した開始境界移動を後続UI処理の失敗で二重適用しない。実際の外部composition終了は引き続き処理する。

復旧で複数キーを再生するときも、確定結果を通知した直後に後続の描画で上書きしない。確定境界の成功後は再生をいったん保留し、入力を順序付きで保持したまま、同じTSFスレッドのメッセージ処理後に再開する。復旧時だけ作るメッセージ専用windowを用い、タイマー・待機・別スレッドは追加しない。再開は文書・composition・世代を確認し、実際の終了/フォーカス変更時は取り消す。

先頭の未完了操作が「選択表記の確定＋継続入力」の場合は、復旧候補による暫定描画を省く。その操作の1回の編集で元の選択表記と新入力を反映し、復旧描画が確定通知のバッファを消さないようにする。他の復旧操作は通常どおり再描画する。

## 再接続・復元

元入力の文字列だけではliteral styleとカーソル/snapshotを復元できない。既存の成功操作ledgerを、Shrinkとsnapshot操作にも拡張する。文節境界変更ではサーバーが返した実際のカーソル移動量を記録する。将来文節の一括準備で最終文節に留まる場合も、実際に保持されたPush/Shrink列を記録する。

再接続時はclear後に同じ入力・編集・文節操作列を再生する。追加のキーごとのRPCやcheckpointのシリアライズは行わない。元のledgerが不完全な既存経路のfallback契約は維持する。

文節操作を含む履歴の再接続は、既存の明示的な復旧経路でクライアント候補cacheを再構築する。古い学習候補IDを再利用しない。サーバー側もsnapshotをclearし、全残余の候補表示に合わせてカーソルを末尾へそろえる操作をledgerに記録してから復元する。

## 検証

`MixedInputConversionTests.swift` は1キーごとの入力、英字の削除/再入力・内挿、部分確定、snapshot復元、`n/nn` と語尾/助詞境界、通常KKCでの候補、Shift+←/→の往復を検証する。各段階でcanonical raw・input count・surface cursor・候補消費数・後続文字列を確認する。

クライアントのledger/reconnectテストと文節状態遷移テストも対象とする。VMは `scripts/vm.py` を使用し、実配布モデルを使うZenzaiの確認と、通常KKC/模擬transportでの確認を区別して記録する。

`MixedInputScenarioCorpus.swift` は実装の語彙から期待値を生成しない独立コーパスであり、技術用語103語×4文脈、複数語/一般用途31文、日本語97例、明示的な英字・記号・識別子等38例を定義する。標準/Windowsテーブル、ON/OFF、1キーずつ/まとめての入力、通常KKCと実Zenzai、削除・再入力・部分確定・snapshot復元を検証する。技術用語12語の全英字境界では、消費数・残り・カーソルだけでなく、選択中候補の英字部分が消費した範囲と一致することも確認する。
