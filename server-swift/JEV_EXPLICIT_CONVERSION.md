# Jevによる明示変換（実験）

設定画面「一般」→「実験的機能」末尾の「Jevによる候補選択」で有効にします。
ON時の警告を確認するとAPIキー入力欄が出ます。保存先は現在のWindowsユーザーの資格情報マネージャーです。
保存・変更・削除はその場で反映され、キーの内容は設定画面へ読み戻しません。
設定JSONでは `general.jev_conversion: true`。既定はfalseです。キーを設定JSONやバイナリには埋め込みません。
資格情報が未設定ならJevへの送信は行いません。評価テストだけは `TYPESAFE_API_KEY` 環境変数を使います。
保存済みAPIキーを使用するRPCは、パイプ接続時に認証された同一ログオンの非制限デスクトップクライアントのみ許可します。Windows検索などのAppContainer・制限トークンのアプリでは通常KKCを使います。同一ログオンの通常デスクトッププロセス間を隔離するものではありません。

有効時は入力中の表示をかなにし、Zenzaiを使わず通常KKCで候補を用意します。
最初のSpace・Tab・変換キーで通常候補を表示し、全文を消費する候補を重複除去して上位16件までJevへ送ります。
送るのは読み、左文脈、候補です。文節分割・文字列生成をJevへ要求せず、全文候補の選択だけを行います。
1件しか選択肢がない場合は通信しません。通常候補は残し、選ばれた候補のIDと消費数も保持します。

通信は入力スレッド外で行い、サーバーのcompositionロックも保持しません。
通常候補は通信中も操作できます。次の入力、候補操作、確定、取消、フォーカス変更があれば応答を反映しません。
2回目以降のSpaceは通常の候補送りで、追加推論しません。
文節操作中や再変換は対象外です。機密・パスワード入力欄、未確定入力の開始位置のscope取得エラーでは送信しません。

入力scopeはTSFの属性追跡APIで未確定入力の開始位置から取得します。パスワード・機密・数値/英数字PIN（PIN設定を含む）が混在するscopeも拒否します。Windows 11メモ帳などで直接の属性取得が失敗する場合にも対応し、開始位置の属性の読み取りや解釈に失敗した場合は外部送信せず通常KKCを維持します。
左文脈は実際の取得元の親contextで、取得範囲全体のscopeを `EnumRanges` で検査してから読み取ります。機密scope、取得エラー、列挙未対応、範囲の欠落がある場合は左文脈を空文字にして候補選択を続けます。文脈の取得自体が失敗した場合は通常KKCを維持します。通常KKC用の文脈cacheは外部送信に使わず、通常KKCの文脈更新経路は変更しません。

通信期限は1500ms。失敗・期限超過・無効応答・サーバー同時要求上限では通常KKCの表示を維持します。
既存のperformance logの `jev_rerank / total` で採点時間・候補数・fallbackを確認できます。
本文やAPIキーはこのログへ保存しません。

## 変換精度評価

`Tests/azookey-serverTests/Fixtures/jev-evaluation.json` の40件を使用します。
同じ通常KKCの全文候補に対して、上位8/16/32件という上限を比較します。
KKCが返した候補数が上限未満なら実際の件数を記録します。探索のN-best設定は通常KKCと同じです。
選択肢が同一なら同じ応答を再利用し、独立した測定数とは数えません。

APIキーに加えて `AZOOKEY_JEV_EVALUATE=1` を設定した明示実行だけが実APIへ接続します。
`AZOOKEY_JEV_EVALUATION_OUTPUT` に結果JSONの保存先を指定できます。
通常のunit test実行時には通信しません。

```powershell
$env:AZOOKEY_JEV_EVALUATE = "1"
$env:AZOOKEY_JEV_EVALUATION_OUTPUT = "$PWD\jev-evaluation-results.json"
swift test -c release --filter jevExplicitConversionEvaluation
```

固定の小規模人工例による探索的評価です。一般利用の精度やZenzaiとの優劣を保証しません。
完全一致の正答率と、正解が候補内に含まれる割合（oracle）を区別し、改善・悪化・fallbackも報告します。

### 実測（2026-09-23、Windows VM）

通常KKC・学習なし・Zenzai OFFで同一の40例を評価し、`jev-latest`への実通信は60回でした。

| 候補上限 | KKC正答 | Jev正答 | oracle | 改善 / 悪化 | Jev中央値 / p95 |
|---|---:|---:|---:|---:|---:|
| 8 | 30/40 (75%) | 36/40 (90%) | 38/40 (95%) | 8 / 2 | 545 / 609ms |
| 16（実装値） | 30/40 (75%) | 37/40 (92.5%) | 38/40 (95%) | 7 / 0 | 531 / 593ms |
| 32 | 30/40 (75%) | 37/40 (92.5%) | 38/40 (95%) | 7 / 0 | 531 / 593ms |

全要求成功、fallbackなし。上限16の実候補数中央値は8.5件でした。
上限32は16と選択肢が同じため応答を再利用しており、独立した改善の証拠ではありません。
KKC生成中央値は30ms。Jev時間はHTTP往復と応答処理を含み、IMEキー入力から描画までの時間ではありません。
測定中には同じVMでRustのコンパイルも動いていたため、厳密な単独負荷ベンチマークではありません。

改善例は「記者に乗った→汽車に乗った」「神を切った→髪を切った」「構成を確認する→校正を確認する」。
失敗には「紙を折った」がKKC候補にない例と、「講演を聞いた」が候補にあるのに「公演を聞いた」を選ぶ例がありました。
完全一致採点では「飴を舐める」は固定正解の「飴をなめる」と異なるため不正解です。評価後に正解表記は変更していません。
約0.5秒の追加待ちを許容する明示変換としては有望ですが、一般的な入力分布・ローマ字操作・実アプリでの使い勝手は別途検証が必要です。

集計は `python scripts/summarize_jev_evaluation.py <結果JSON>` で再現できます。

一方、Notepadの起動直後には入力scope取得が失敗してKKCへfallbackする場合があり、TSFの再起動後に実通信が成功しました。この環境依存の再現条件と、機密入力欄の実操作による送信抑止は追加検証が必要です。

APIキー設定の追加では、Windows資格情報マネージャーのGeneric credentialを使用します。APIキーは同じWindowsユーザーで起動する設定アプリとIMEサーバーから参照され、通常の設定JSONには含まれません。
ネットワークログオンのSSHでは資格情報セットが存在せず、`CredWriteW` は `ERROR_NO_SUCH_LOGON_SESSION` を返しました。
資格情報の保存・読取・削除の往復テストは対話ログオンでの実行が必要です。
